The hardwired decode core

A static program of macro-operations drives two fully pipelined units. Every arithmetic unit is a pipelined binary32 add/multiply (latency 5, one result per cycle); there is no divider, no iteration and no stall on any path. The arithmetic order is a golden specification, so the RTL is bit-exact with it.

DeepSeek-V4.1 throughput and energy

ROM wafer: the same package, stitched on one wafer

Array or wafer?

Both use the identical package. The array wins per-user speed and yield flexibility; the wafer holds the whole model with shorter hops and wins aggregate throughput and tokens per joule (3.18× throughput, 3.97× tokens/J best-vs-best at 200K for V4.1).

V4.1-specific units already built and bit-exact against the V4.1 golden, all closed on ASAP7: FP8/FP4 block-linear lane (1.20 GHz), activation quantiser (1.13 GHz), top-k SELECT (1.62 GHz at K=6, 1.12 GHz at K=512), Engram hash (1.52 GHz), softplus/sqrt (1.03 GHz).

HBM machine: a general accelerator

Why ROM wins, and where it stops

Weights read from ROM next to the arithmetic cost no HBM bandwidth and little energy; specialised links and a static schedule remove software and collective overhead. The advantage shrinks when per-user state dominates — long-context KV caches, recurrent state, uncompressed attention — because ROM does nothing for that traffic.

Control path: in the decode core the sequencer is under 2% of a token; on the HBM machine the control path has repeatedly been the limiter (clock, issue latency, issue rate), and an optimisation pass is in progress.
