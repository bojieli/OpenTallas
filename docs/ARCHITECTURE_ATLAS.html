Hardwired-ROM decode machines for fast per-user inference

Mask-ROM weights beside the multipliers and a compiled, fully pipelined decode dataflow, built for a small interactive model (Qwen3-8B) and a large sparse long-context model (DeepSeek-V4.1-Flash), with an HBM comparator on the same core.

1Abstract

Interactive and agentic use of language models is gated by per-user decode speed, which batching does not improve. We find that on HBM accelerators this speed is bounded twice: by streaming every active weight across the memory interface once per token, and on GPUs by the microsecond cost of each dependent operator boundary. We present OpenTallas, a model-specific architecture that stores weights in mask ROM beside the multiply-accumulate lanes and executes decode as a compiled dataflow of fixed-latency pipelined units. We build it for two representative workload classes, a small interactive model (Qwen3-8B) and a large sparse model with compressed KV for long context (DeepSeek-V4.1-Flash), and add the pipelined units their irregular operators require. Reduced configurations of both decode bit-exactly in RTL, and the token-path units route at about 1 GHz on ASAP7. A bottom-up critical-path model places the single-reticle Qwen3-8B design more than an order of magnitude above the weight-streaming ceiling of a current GPU for one user; the multi-die System-2 design is being re-evaluated under realistic packaging.

2Introduction

An interactive user, and increasingly an agent calling a model in a loop, waits on decode: tokens are produced one at a time, each depending on the last. What matters is therefore the rate for one user. Serving systems have largely optimised aggregate throughput through batching, which amortises weight reads across users but does not make any single stream faster.

Current hardware falls short of what one user could get, for two reasons that we quantify in §4. First, an HBM accelerator must read every active weight once per token, which caps a single user at a few hundred tokens per second for an 8B model even on the fastest current part. Second, a decode token is a chain of several hundred dependent steps, and on a GPU each step that gathers from the whole chip costs about a microsecond of synchronisation through the L2 cache, which we measure directly. Hardwired silicon has been reported to exceed these limits by more than an order of magnitude for an 8B model [HC1], which suggests the gap is architectural rather than physical.

Our thesis is that when a model is fixed, both its weights and its schedule can be hardware. Mask ROM beside the lanes makes weight bandwidth a function of silicon area, and a schedule compiled before fabrication replaces run-time synchronisation with sequencing measured in cycles. Per-user latency then becomes the critical path of the decode dependency chain, and the design problem becomes shortening that path while keeping every operator exact. The approach has real costs, a mask set per model and capacity that scales with die count, which we treat as first-class constraints (§5, §10).

This report makes the following contributions:

  • A characterisation of fast per-user decode as four challenges — the memory wall, serial dependency, multi-die scaling and irregular exact operators — each tied to a design principle (§4, §5).
  • A hardwired decode core whose schedule is the program, verified bit-exactly through a golden → ISA → program → RTL chain (§6.2, §7.1).
  • Fixed-latency pipelines for the irregular operators of modern sparse models, and fixed-order collectives for multi-die tensor groups (§6.3, §6.5).
  • A critical-path performance model priced with routed RTL depths, and a measured GPU dependent-boundary cost for the comparison (§8).
  • Implementation evidence on ASAP7: routed units, memory compilers with self-test and repair, scan and ATPG, a hierarchical full-chip flow and an OpenAI-compatible host interface (§7).

3Background

3.1 Anatomy of one decode token

A decoder-only model produces one token per step. Each of its L layers applies, in order: a normalisation; projections of the hidden vector into queries, keys and values (matrix-vector products against the layer's weights); attention of the new query over every stored key and value of this user's context (the KV cache), appending the new key and value; an output projection; a second normalisation; and a feed-forward block (dense, or a mixture of experts of which a router picks a few). A final normalisation and a vocabulary projection produce logits, and the chosen token becomes the next step's input.

  • Every step depends on the one before. A matrix-vector product needs the whole previous vector; softmax needs every score; the next token needs every logit. A token is a chain of on the order of ten dependent steps per layer.
  • At batch 1 each weight is used once per token. Two FLOPs per weight read, so the work is bandwidth-bound, not compute-bound.
  • Per-user state grows with context. The KV cache is read every step; its size per token decides whether long context is a bandwidth problem of its own.

3.2 Representative workloads

Deployed systems increasingly pair two classes of model. A small, fast "System-1" model holds the interaction: it must answer within human conversational latency. A large "System-2" model does deeper work in the background and is delegated to when needed. OpenAI's GPT-Live (July 2026) keeps continuous voice interaction on a low-latency model and delegates search, reasoning and agentic work to GPT-5.5 running in the background [GPT-Live]. Thinking Machines Lab's interaction models (May 2026) state the same split: "when a task requires deeper reasoning than can be produced instantaneously, the interaction model delegates to a background model that runs asynchronously" [TML]. Both classes are latency-bound: the first for the user's turn, the second because agentic loops chain many calls.

We therefore pick one representative of each class rather than the models most favourable to ROM:

  • System-1: Qwen3-8B [Qwen3], a widely used dense GQA model of the size class used for fast interaction. It is also small enough to test the single-die case (C3).
  • System-2: DeepSeek-V4.1-Flash, a large sparse mixture of experts (552 B total, 16 B active) with compressed KV for a 1 M-token context. It carries the architectural line frontier open models are following for long context: latent/compressed KV (MLA, DeepSeek-V2 [DS-V2]), sparse attention selected by a learned indexer (DeepSeek-V3.2 [DS-V3.2]), compressed sparse attention to one million tokens (DeepSeek-V4 [DS-V4]), plus manifold-constrained hyper-connections with a Sinkhorn projection [mHC] and Engram conditional-memory lookup [Engram]. If future frontier models follow this line, their decode will look like V4.1's: small active weights, fixed attention work per token, and many irregular operators (C5).

Selection criteria, applied to every profiled candidate. (1) Class: is it a representative System-1 or System-2 model? (3) Per-user state: does per-token state traffic stay small at long context, or does it dominate regardless of where weights live? (4) Architectural novelty relative to the other target. (5) ROM capacity at the analytical model's density.

  • Qwen3-8B is shallow and wide: about 12 dependent steps per layer, dominated by the matrix passes. A fast matrix engine and short softmax/SiLU pipelines set its token time.
  • V4.1 fixes its attention work per token at 640 rows, whatever the context, and moves the context-dependent cost into the indexer on 8 layers. Its MoE touches only 6 of 384 experts, but a ROM machine sweeps all of them (C3, §4).
  • V4.1 needs five unit types beyond the matrix engine and stream unit: FP8/MXFP4 block-dot lanes, SELECT (top-k, router top-6, candidate blocks), a Sinkhorn unit, the Engram hash-and-gather unit, and the IEEE divide/sqrt/softplus functions. Its dependency chain per layer is about twice Qwen's.

4Motivation: four challenges

We identify four challenges that together bound per-user decode speed. The first two apply to any single device; the third appears once a model spans many dies; the fourth comes from the structure of modern models themselves. Each ends with an implication that a design principle in §5 answers. First-order derivations are collected in Appendix D.

4.1 Challenge 1 — The memory wall sets the per-user ceiling

Every token touches every active weight, so where the weights live — their bandwidth and their capacity together — bounds single-user speed.

At batch 1 each weight is used for exactly one multiply-accumulate per token, so decode performs about one floating-point operation per byte of weight read. An accelerator that keeps the weights in HBM therefore runs at the speed of its memory interface, not its arithmetic: the per-user rate cannot exceed memory bandwidth divided by the bytes a token must read. Batching raises aggregate throughput by reusing each read across users, but it leaves the rate of any one user where it was.

The ceiling is low for both workload classes. For the System-1 model it lies in the hundreds of tokens per second even on the fastest current HBM part, and a sparse System-2 model does not escape it: its active weights per token are comparable to a dense 8B model's (Figure 4-1). Moving the weights next to the arithmetic changes the picture qualitatively, because on-die memory bandwidth grows with the number of memory macros rather than with the number of package pins.

The difficulty is capacity. On-die storage must hold the whole model, and the densities differ by an order of magnitude between memory technologies (Table 4-1). We find that even the System-1 model does not fit one reticle at BF16; a one-die product needs about 4-bit weights, as the only published hardwired product also uses [HC1]. SRAM-only storage would need about a dozen wafers for the System-2 model.

4.2 Challenge 2 — Per-user latency is a serial dependency problem

Once bandwidth is solved, a token's time is the critical path of its dependent operators, and on a GPU each dependent boundary costs on the order of a microsecond.

A decode layer is a chain: each matrix-vector product needs the whole output of the previous step, softmax needs every score, and the next token needs every logit. The System-1 model has about a dozen dependent steps per layer and the System-2 model about twice that, so a token is several hundred dependent boundaries long. When weights no longer bound the rate, the cost of crossing each boundary does.

We measured that cost on a Blackwell GPU (Figure 4-2). The key finding is that the expensive part is not kernel launch, which programmatic dependent launch and persistent megakernels already remove, but the physics of the dependency itself: a result produced by every streaming multiprocessor must pass through the L2 cache, and a memory fence must wait for L2's acknowledgement. The cheapest all-SM boundary that actually delivers the activation vector costs about a microsecond, and none of the alternative designs we tried — data-carried flags, per-producer flags, cluster hierarchies, or Megatron-style operator pairing — was faster. Only dependencies that stay inside one SM or one cluster are cheap, and a matrix-vector product spread over the whole chip cannot stay there.

A machine with a fixed model can avoid the problem rather than optimise it: when every dependency is known at build time, a sequencer can issue the next dependent operation in a few cycles and start a consumer as soon as its producer has written enough elements.

Implication. The schedule must be resolved at build time so that dependent operations are sequenced in cycles, not synchronised in microseconds.

4.3 Challenge 3 — Scaling past one die must not add latency

Frontier models span many dies, so communication, collectives and packaging enter the critical path of every token.

A System-2 model needs tens of reticle dies (Table 4-1). Splitting it adds two kinds of serial cost: pipeline hops, where a token's activations move from the dies holding one group of layers to the next, and collectives, where the dies of a tensor group combine partial results inside a layer. Both are latency-bound, because decode activations are kilobytes, not megabytes. We find that if every die keeps its own weights and only activations move, communication is under a tenth of a token under realistic link assumptions (Table 4-2); the design must keep it that way by making collectives small, fixed and few.

Packaging is a hard constraint rather than a parameter. High-density die-to-die links reach only adjacent dies, board links pay forward-error-correction latency, and interposers are limited in size: four reticle-sized dies with their HBM exceed the largest interposer in volume production and need the class announced for 2025–26 [CoWoS]. The packaging choice is therefore evaluated, not assumed (§6.5).

4.4 Challenge 4 — Modern models are irregular, and hardwiring must stay exact and fast

MoE routing, top-k indexers, Sinkhorn-normalised hyper-connections, Engram lookups and sparse attention must become fixed-latency pipelines at about 1 GHz while matching the reference bit for bit.

The System-2 line of models adds operators that are neither matrix products nor element-wise functions, and each sits on the critical path (Table 4-3). They are data-dependent selections, iterative normalisations and hashed lookups — exactly the operations a conventional datapath implements with loops, sorts and iterative dividers. Built that way they cost the design 10–20% of its per-user rate; each needs its own pipeline.

The same operators make exactness hard. Floating-point addition is not associative, so a different reduction order is a different model, and faults in selection or indexing produce fluent but wrong tokens. The full-scale compiler lane found three such faults only by comparing against the reference token by token (results/abi3/deepseek_v41_pool_and_decode_path.json). Exactness also has a price: relaxing the golden order would buy about 15% (§8.5), which we decline. Finally, every one of these units must close timing near 1 GHz on a 7 nm-class process, where a single combinational binary32 addition already takes several nanoseconds.

5Key insights and design principles

5.1 Central insight: when the model is fixed, weights and schedule can be hardware

The key insight is that the two limits of §4.1 and §4.2 share a cause: a general-purpose accelerator must treat both the weights and the schedule as data, fetched and synchronised at run time. For a model that will be served unchanged for months, both can be fixed at fabrication. Weights then become mask ROM placed beside the multipliers, and the schedule becomes a compiled program whose dependencies are resolved before the chip is built.

This removes the memory wall rather than moving it. Each ROM macro delivers a word per cycle to the lanes next to it, so aggregate weight bandwidth grows with silicon area, not with package pins. A ROM bit is also denser than an SRAM bit and far cheaper to read than an HBM access (Table 5-1), which is what lets a System-1 model fit one reticle and a System-2 model fit tens of dies rather than many wafers. With the weights no longer re-read per user, a single user keeps the lanes busy: batching becomes a way to add aggregate throughput, not the price of efficiency.

The insight has costs that bound where it applies. Each model and version needs its own mask set; capacity scales with die count; the KV cache is per-user state and still lives in SRAM or HBM; and long-context attention traffic is untouched by ROM, which is why the workload's state per token matters (§3.2).

Sinkhorn unit. The mHC mix projects a 4×4 matrix onto the doubly stochastic set with 20 Sinkhorn iterations [mHC]. Threshold select. Instead of sorting, the unit counts the high bytes of streamed scores in a 256-bin histogram, walks a tree to the bucket holding the 512th value, refines it on the low byte, then keeps everything above the threshold plus ties in position order. 6.6 HBM comparator variant

The comparator isolates the memory technology: it is the same hardwired core with weights and KV streamed from HBM, so any difference is due to where the weights live, not to control.

The comparator core

  • The analytical comparator is a B200-class GPU executing decode as a fused megakernel/PDL sequence, with each remaining dependent boundary charged at the measured Blackwell cost (§8.4).
  • The RTL comparator is the HDC itself with weights and KV in HBM: ot_hdc_kv_stream prefetches KV so the engine never stalls, and the reduced Qwen3 token stays bit-exact (results/rtl/hdc_kv_stream_campaign.json).
  • A weight streamer (rtl/hdc/hbm/) that prefetches weights per pseudo-channel is built and bit-exact on its branch; its campaign record and routed clock are not yet on main.
The comparator gets the same hardwired dataflow, so the measured difference is the memory technology, not the control path.

8Evaluation

8.1 Methodology

Three evidence classes, tagged on every headline figure. : Verilator simulation of the RTL, OpenROAD routes on ASAP7, and a Blackwell GPU benchmark, each a committed record with source hashes. : the bottom-up critical-path model (tools/decode_critical_path.py), which prices each layer's operator graph with routed unit depths at the slowest routed token-path clock (1.034 GHz), every collective by latency, algorithm and bytes, and control per instruction. : an experiment in flight, named with the record that will settle it.

Calibration. The only published hardwired point is HC1 (Llama-3.1-8B, 16,960 tok/s per user, self-reported [HC1]). The model gives 10,103 on an HC1-class die, 0.60× of published, so its absolute figures are pessimistic; the graph-priced analytical model gives 10,723 (0.63×).

8.2 Decode-core cycles per token

We find that the compiled core decodes both reduced models bit-exactly and that most of the remaining cycles are unit busy time rather than control: sequencer issue cost is a few percent of the token. Chaining consumers on producer progress and spreading attention over all lane groups gave the largest gains (Figure 8-1); pipelining across packages scales aggregate throughput nearly linearly while keeping each user exact.

Wafer-scale integration

What it was. The V4.1 package logic laid out as reticle fields stitched on one wafer, so a die-to-die hop becomes an on-wafer crossing, with KV in HBM stacks around the wafer edge.

First principles. The per-user rate is bound by the serial dependency chain and the ROM sweep, not by link bandwidth (C4: interconnect is under a tenth of the token). A wafer's advantage is shorter wires, but a wafer-sized tensor group spans many more fields, so every collective crosses more of them; a 125 ns field crossing on a published mesh makes collectives two-thirds of the token. The wafer only matches the array when a crossing costs about 13–18 ns, which needs a designed long-wire fabric; our routed express link (605 ps/mm with a register per mm) makes a 28.55 mm crossing ≈30–35 ns.

9Related work

GPU decode. Serving stacks capture decode in CUDA graphs and fuse element-wise work into neighbouring kernels; Programmatic Dependent Launch overlaps a kernel's prologue with its predecessor. Megakernels run a forward pass as one persistent kernel whose instructions wait on counters in memory: Hazy Research's Llama-1B megakernel [Hazy] and the Mirage Persistent Kernel [MPK]. They remove launch overhead but keep the weight stream (C1) and the L2 round trips of cross-SM dependencies (C2), which we measure directly.

On-chip-SRAM dataflow machines. Groq's tensor streaming processor makes execution deterministic by removing reactive hardware (arbiters, caches) and scheduling everything in the compiler [TSP], a principle we share (P2, P5). Cerebras keeps weights in on-wafer SRAM (vendor-reported 44 GB on 46,225 mm² for WSE-3 [WSE-3]). Both trade capacity for bandwidth with SRAM; ROM's density advantage (I-c) is what lets a large MoE fit tens of dies rather than many wafers. SambaNova (tiered SRAM/HBM/DDR reconfigurable dataflow), Tenstorrent (mesh of programmable cores) and d-Matrix (SRAM digital in-memory compute) occupy other points of the same trade-off [citation needed].

Model-specific silicon. Etched builds a transformer-specific datapath that keeps weights in HBM [citation needed]. Taalas HC1 hardwires Llama-3.1-8B on one 815 mm² TSMC 6 nm die and reports about 17,000 tokens/s per user [HC1], the closest prior work and our calibration anchor. We differ in targeting a large sparse System-2 model across dies, in publishing a bit-exact verification chain and implementation evidence, and in pricing the comparator with measured GPU boundary costs.

10Discussion and limitations

When ROM is the wrong answer. The architecture assumes a model is worth a mask set. Models that change weekly, or whose per-user state traffic dominates (recurrent state or full KV at long context, Table 3-1), gain little: ROM removes weight traffic, not state traffic. The System-1/System-2 split helps here: the interaction model changes slowly and is latency-critical, while the background model can be swapped behind it [GPT-Live].

What is modelled rather than built. The per-user rates are model outputs calibrated only against one self-reported product; the clock is the slowest routed unit, not a closed core; memory macros are model-grade views on a predictive PDK. The GPU boundary costs are measured on a workstation Blackwell (GB202), not a B200.

11Conclusion

Fast per-user decode is limited on today's accelerators by weight bandwidth and by the synchronisation of a long dependency chain. Fixing the model in silicon addresses both: mask ROM beside the lanes turns weight bandwidth into a function of area, and a compiled schedule of fixed-latency units turns synchronisation into a few cycles. We built the decode core and the units a modern sparse long-context model needs, verified them bit-exactly against golden models, and routed them at about 1 GHz on ASAP7. What remains to settle is the whole-core clock, the packaging of the multi-die array under realistic links, power sign-off, and the comparison ratios with measured GPU costs; each is marked pending with the record that will settle it.
