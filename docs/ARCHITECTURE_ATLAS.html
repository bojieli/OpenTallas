1Introduction

Purpose. Define the architecture of the ROM inference machine family, the design rules its blocks follow, and the evidence each claim rests on. Numbers in this document are copied from committed simulation, place-and-route and analytical records; each section names its source.

Scope. In scope: the hardwired decode core (HDC), its instruction set and numerics, the chip-to-chip link and array/wafer systems, the DeepSeek-V4.1 package, the analytical comparison with the HBM machine. Out of scope: analog PHY design, packaging, test/DFT, power delivery.

3Architecture principles

IDPrincipleConsequence in the design
P1Weights are hardware.Weight ROM words are laid out in the exact order the engine streams them; address generation is a counter.
P2Every datapath unit is a fixed-latency pipeline with II = 1.No divider, no iterative unit, no combinational IEEE op; special functions are unrolled Horner/Newton chains.
P3Nothing stalls.Memories answer at fixed latency; units never back-pressure; a program is scheduled so no read can overtake its write.
P4The schedule is the program.A static list of macro-operations; the sequencer does no admission, dependency search or interpretation at run time.
P5The arithmetic order is specified.A golden model defines every rounding in hardware order; RTL is bit-exact with it; order changes (K-split, BF16 KV) are spec changes, re-validated against the model's reference tokens.
P6Overlap by measured progress, not by barriers.Units report elements/slots produced; a consumer starts at a threshold derived from producer write order and consumer read order.
P7Fail closed.Nonfinite operands, overflow and inexact BF16 products raise a sticky fault instead of producing a value.
P8Register every boundary.Unit, memory and link ports are registered on the block side; wide buses get an extra register at the pins.

4.2 Matrix engine

Output n of tile t sits in lane l of slot j of group g. Each lane multiplies then adds into a sum that re-enters the adder exactly IL = 8 cycles later, so every output accumulates its products strictly in order at one multiply-accumulate per lane per cycle, with no accumulator file.

weight  = lane g·W+l of word   wbase + r·ts + k·ks + (j ≫ jsh)·js        (KV ops: wbase + t·ts + …, own port per group)
x       = element              xbase + c·xcs + k·xks + j·xjs              (BF16-rounded when round=1)
result  = lane l of word       obase + t·ots + j·ojs                        after the last k of the chunk
valid   = (t·IL + j)·W + l < nout   (rows)      or      t·W + l < nout   (lanes: one vector per slot, e.g. a head)

4.4 Sequencer and control path

The control path is deliberately thin: one in-order issue slot, no dependency search, no admission. Hazards are resolved at program-generation time into one of three issue conditions.

6.3 ROM wafer

Wafer versus array

  • Same package logic; die hops ≈10 ns (UCIe-class) instead of ≈100 ns package hops.
  • Holds the whole V4.1 model; wins aggregate throughput and tokens/J (3.18× / 3.97× best-vs-best at 200K).
  • Needs the fabric router with multicast and deadlock-free mesh routing (in design), and yield/redundancy handling (not started).
  • Partitioning rule: a package boundary never separates a KV-source layer from the layers reading its compressed KV; Engram tables get their own tiles.

6.5 DeepSeek-V4.1: logical datapath of one token

Forty layers, each an attention half and a MoE half joined by hyper-connections (a four-copy residual stream). Layers share state in groups: layers 2–7 read layer 2's compressed KV and index selection, 8–13 read layer 8's, 14–19 read 14's, and 20–39 read layer 20's compressed KV and candidate-block mask. Layers 1 and 14 add Engram n-gram lookups from their own read-only tables. The partitioning follows from this: a package boundary never separates a KV source from a consumer it cannot reach cheaply.

6.6 DeepSeek-V4.1 ROM array: physical layout and network

Selected configuration (the study is in §6.8): 188 reticle-sized dies of 815 mm² in 47 packages of four. Each package is one tensor group: its four dies split every weight matrix they hold, including a quarter of every expert, and combine their partial results with one-shot collectives over UCIe. In a one-shot collective every die sends its partial to the other three and sums locally in a fixed order, so each die holds the identical, bit-exact result after a single ≈10 ns link crossing. The packages are joined by board SerDes in a ring: a 40-stage layer pipeline, one layer per package, whose closing link returns the token to stage 0. Each die streams its KV cache from five HBM3E stacks. The Engram tables, embedding and lm_head take the remaining ROM capacity; their exact placement is not yet fixed.

6.7 DeepSeek-V4.1 ROM wafer: datapath and layout

Selected configuration: twelve wafers of 46,225 mm², each holding 57 reticle fields. The earlier analytical design made the whole wafer one tensor group, and at 125 ns per field crossing its six collectives per layer then cost ≈336 µs per token, two-thirds of the token time. The selected design splits each wafer into three square groups of 19 fields. Each group is a tensor group that reduces with one-shot collectives over its own compact region, and the 36 groups form an on-wafer and wafer-to-wafer pipeline. Each wafer has 43 HBM3E stacks at its edge for KV. The wafer's strength remains aggregate throughput, ≈1.0 M tok/s at 4,096 users. Per user it is still behind the array, because a field crossing costs 125 ns against 10 ns for UCIe.

6.8 Communication topology selection and the decode critical path

The analytical model prices a layer's serial work as four dependent passes (≈250 ns) plus two all-reduces. The bottom-up model tools/decode_critical_path.py replaces that with each layer's operator dependency graph. Every node is priced with our routed ASAP7 unit depths at 1.034 GHz, from the matrix engine, the stream-unit functions, the V4.1 select, the softplus/sqrt and the divider. Every collective the weight split needs is priced for latency, algorithm and payload bytes, and the control path is priced per instruction. Against the published Taalas HC1 (Llama-3.1-8B) it lands 1.67× slower (98 µs against 59 µs per token), so its absolute numbers are pessimistic. The analytical model is 1.45× optimistic on the same anchor, so the truth lies between the two.

The sweep. 2,038 configurations at fixed silicon. The array was swept over 2, 4 or 8 dies per package; board fabrics chain, ring, mesh, torus, fully connected groups of 2, 4 or 8 packages, or one switch; tensor groups of 1–32 dies; and six reduction algorithms. The wafer was swept over groups of 4–57 fields in square and rectangular shapes. Both were run with experts either striped across the group or placed one per device. The results:

  • The array is insensitive to its network. The best configuration (8-die packages, 8-die group, ring) reaches 4,262 tok/s per user, only 3% above the selected 4-die ring. That group gives up a quarter of the aggregate at 4,096 users (379 K against 504 K tok/s) and needs a 6,520 mm² interposer. A single switch tier costs 3–6%.
  • The wafer is sensitive to its group size. The per-user rate goes from 1,997 tok/s with one 57-field group to 2,779 with three 19-field groups. Groups of 8–12 fields reach about 2,950 but leave 2–16% of the fields holding no weights.
  • One-shot wins almost everywhere at decode payloads (1.5–68 KB). Every static algorithm keeps a fixed summation order, so results stay reproducible.
  • Placing each expert on its own device is 11% slower than striping at batch 64. It also needs arrivals buffered and summed in expert-id order to stay bit-exact.

What this changes in the design. The per-user bound for V4.1 is not bandwidth, links or control. It is the hyper-connection Sinkhorn: 39 dependent normalisation steps of 4×4 per sublayer, 80 per token. Each step is a sequential four-term FP32 sum, an eps add and an IEEE divide, ≈51 cycles or ≈2.1 µs per sublayer at our unit depths, which caps the rate near 6,000 tok/s whatever the silicon. A latency-optimised Sinkhorn unit, bit-exact to the golden, is therefore the next RTL priority. After it come the index top-k merge (≈3.8 µs on each of the eight index-source layers) and the stream-unit functions on the norm and softmax chains (sigmoid 172, exp 121, rsqrt 90 cycles). The analytical model is being corrected to use this critical path and collective census for every target, including the GPU side, and the tables above will be regenerated from it.

8HBM comparator

ABI 3.0 RTL (the general machine)

  • Descriptor control plane, microsequencer, admission bridge and IEEE engines; the reduced Qwen3 token runs end to end (7.9 M cycles, one MAC per cycle).
  • Its control path has repeatedly been the limiter: clock (58–75 MHz slowest blocks), issue latency, and issue rate on many small operations. A control-path optimisation pass is in progress (§12, I-6).
  • Shipped-model RTL stops at PC 32 DMA.SCATTER.
Specialisation is a property of the ROM machine. The HBM machine keeps GPU-class NVLink numbers in every comparison.
