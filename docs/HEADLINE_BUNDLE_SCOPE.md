Superseded Qwen figures:
- **10,874 tok/s AR and 18,720 tok/s DFlash** are the TP-2 two-reticle package with DFlash (`results/arch/qwen3_budget.json`). That design is not the adopted TP-4 AR target, and its rates assume the KV is perfectly overlapped. `summary-r1.json` refuses the comparison (`refused_comparisons.atlas_headline_TP2_DFlash`).
- **8,460, 6,222 and 10,262 tok/s** (MICROARCH_MODEL.md) are compute-chain compositions with no KV-delivery term. The 6,222 row also mixes positions: its body ratio is measured at position 0 but applied to the 8K chain (`refused_comparisons.microarch_6222_mixed_position`).
- **≈ 9,700 / 9,851 tok/s** (option C and TP-2 model rows) have the same missing KV-delivery term.

**What the TP-4 exact token proves.** The retained TP-4 position-zero exact token ([`verification_replay.json`](../results/rtl/qwen_rom_TP4_terminal_20261002/verification_replay.json)) proves the datapath and numerics only. Its runtime die wrapper ties the KV, weight and embedding readiness inputs high: `kv_write_drained`, `kv_ok`, `w_ok`, `emb_ok` and `me_mem_ok` are `1'b1`, and the embedding ROM ports are zero ([`ot_qwen_rom_rt_die_w12.sv:151-165`](../rtl/test/qwen_rom_runtime/ot_qwen_rom_rt_die_w12.sv)). It carries no KV-service, weight-delivery or embedding-delivery timing, so it is not evidence for any rate above.

KV traffic at the calibrated design point is **150,690,816 B read** and **156,672 B written** off chip per die per token (`baseline-r1.json` `identity`). The 150,847,488 B figure some documents cite is RD+WR command bytes (4,713,984 × 32 B), not KV payload.
