# V4.1 full-shape HBM address and capacity preflight

The deployed pooled index-key writer sends each key to all four HBM stacks (`w_stack_mask=4'b1111`). Its code plane takes 64 B per key; eight keys share one 32 B scale sector, yielding 68 B per key on **each** stack. The adopted capacity model divides this 68 B by four, as if the keys were striped. The compressed KV is already charged as striped.

At the 1M, ratio-1 layer-20 design point, one die owns 262,144 keys per user. With the current writer, each of its four stacks holds 17,825,792 key bytes per user, in addition to 18,874,368 compressed-KV bytes and 33,792 window-KV bytes. At 22.5 GB per stack with the adopted 0.9 reserve, that placement holds **551 users**. The model's striped-key placement holds **866**. This is a static placement check, not a full-shape simulation or a revised throughput estimate. The reproducible, source-pinned calculation is in `results/arch/v41_hbm_region_preflight.json` and `tools/v41_hbm_region_preflight.py`.

There are two coherent resolutions. The pooled indexer and key bridge can shard keys across stacks, retaining the 866-user model capacity after an exact key-scan and timing gate. Otherwise the capacity model must price four copies and cap the saturated point at its lower limit. A physical layout with per-user alignment or additional metadata can lower either limit further.

The writer and scanner also lack a user-slice offset. The writer derives its code and scale sectors from `rbase` and `row`; the scanner derives its base from `wbase-cfg_ik_base`. The die reserves `KEY_USERS*IKH_SLICE` sectors but does not feed a user base into either address calculation. Two users of one layer therefore alias their index-key image even when the reserved region is large enough. The chosen mapping must add the same user offset to both writer and scanner and prove read-after-write isolation for at least two users.

The current 28-bit index sector address reaches at most 481 users of replicated key slices; the 551-user replicated-capacity point needs 29 bits. Both 551 and 866 users need a 10-bit user ID, while the package controller has an 8-bit `cfg_users`/header user field and `MAXU=16` by default. A full-mode controller needs separate token, position and index header fields: using `NW=21` in the current layout overlaps POS/IDX by 5 bits and IDX/VAL by 5 bits; a 17-bit token overlaps ADDR by one bit. Its KV user base also needs a die-physical width independent of the core's A=30 field.

The published die is still the reduced vehicle (`AW=24`, K-sector `HAW=28`, `KV_AW=15`, unpacked KV); it does not implement the full-shape geometry. Claude owns the die-side packed KV, HBM port/address and controller migration; the full-shape core/ISA owner supplies A/N/PW/TW/CIDW and the word-addressed KV descriptor. The full-shape ROM must be word-addressed: 2.714 GB is about 21.2M 128-B words (25 bits), while BF16 element addressing needs 31 bits. The vector unit's direct ROM element source needs either a low-2^24-word placement rule for the embedding or a wider element address.

The reduced die derives `KV_SECTORS` with a 32-bit `integer` expression `2*((KV_USERS << KV_AW)/4)`. Directly raising its unpacked per-user `KV_AW` to 26 for 866 users creates 58.1 billion word slots before the shift, beyond 32 bits. The packed-layout migration must derive the region in checked 64-bit sector arithmetic before narrowing the physical address; otherwise a wrapped region size can defeat the overlap and capacity assertions.
