Open research · inference silicon

Weights in ROM, beside the multipliers.

OpenTallas designs inference chips that store a model's weights in mask ROM next to the arithmetic. There is no weight traffic from memory, and each user's tokens stream at hardware speed. The designs cover a Qwen3-8B ROM die, a DeepSeek-V4.1 Flash ROM array and an HBM accelerator. Each one is taken down to RTL and per-block place-and-route.

NOT BUILTNo OpenTallas chip exists. Every chip rate on this page is an analytical estimate, composed from RTL simulation and per-block physical design in a predictive 7 nm kit. Each rate carries its source file and date. GPU rates are published third-party figures.

Why this matters

Most voice assistants still route requests through scripted intent pipelines rather than an LLM that reasons and calls tools. Decode latency is one major reason: a reasoning model that thinks for a few hundred tokens at GPU per-user rates takes seconds. Cost, reliability and privacy matter too. Faster decode does not fix those, but it does remove the wait.

Demo D · DeepSeek-V4.1 Flash · generative UI

An app that writes its next screen

In a generative UI there is no fixed interface. After every click the model reasons, calls tools, and then writes the next screen as HTML or patches the one on screen. These are real sessions with DeepSeek-V4.1 Flash in three apps. Each action replays at four per-user rates, and each lane renders the model's HTML as it streams. The first interaction (a full screen) and the follow-ups (patches) are measured separately.

DeepSeek-V4.1 Flash

Replay model. Each recorded model call becomes prefill, then decode, then the call's tools. Prefill uses the uncached prompt tokens the API reported, at a published GPU prefill rate, on both sides. Decode uses every generated token (reasoning, text and tool-call JSON) at the side's per-user rate. Tools use their measured wall time. Harness overhead between steps is left out on both sides.

What is not modelled. The KV handoff from the prefill GPU to the chip is not charged. It is a few milliseconds per turn at these prompt sizes (results/arch/prefill_ingest.json). The chip rates are measured at the designs' target context (8K for Qwen, about 1M for DeepSeek), which is longer than these sessions, so they are conservative for short contexts. Token counts come from the model the API served (deepseek-flash).
