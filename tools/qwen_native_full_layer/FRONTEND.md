# Exact external-kernel integration candidate

`ot_qwen_tp8_native_services_frontend` composes the source-pinned real SU-write formatter, actual sequencer-store row assembly, eight-chunk FP32 Q VM reader, native request ownership, and addressed 32-word attention VM commit bridge. The frontend is a separate candidate top: production defaults and historical source identities are untouched.

Its kernel ports must connect to the compiled actual `ot_qwen_tp8_attention_service` model. `kernel_request_valid` records actual admitted native dispatch; Q is emitted exclusively by the actual Q reader from tagged VM responses. `kernel_result_valid/data/identity` comes from the actual kernel. There is no exponent, reciprocal, golden-result, or synthetic completion injection surface inside this control top. A test harness supplying these ports must state its kernel/source identity and may not call an isolated frontend fixture a whole-layer run.

Native readiness requires the exact descriptor QR13696 / ATTN word3167 / nout512 / k128, a source-validated fused-program capability, all eight current K/V quarter write completions, an available Q reader, and actual kernel readiness. Native completion requires both the kernel's accepted result stream completion and all 32 separately observed VM commit acknowledgments. Epoch admission is blocked until the preceding native request is fully idle. Raw FP32 Q transport remains lossless.

The actual memory wrapper must obtain all four per-row ACKs from physical write completion, not credit return. The native physical layout stores four 32-byte dimension quarters per128-byte row. The provider's historical four-full-row-replica fixture is only a fence mechanism proof. The external row write/read provider and native kernel K32/V4 request transport are bound in the full-layer C++ harness, including their real controller clocks and actual DRAM codewords.

The compiled external frontend library reuses a separately compiled immutable kernel rather than duplicating a large kernel build. Cross-model interfaces must settle during the same low phase before simultaneous rising edges. An added registered stage must be recorded explicitly if used. Startup-fixed kernel593 supports a functional baseline; registered result-face successor b2 requires its own verdict and cannot inherit593's receipt.

Current evidence is **library build only**: EPYC1 `oth-ubuntu-1246238-1791960160`, ot-run exit0, reservation4GB/4threads.
