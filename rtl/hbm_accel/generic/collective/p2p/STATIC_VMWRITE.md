# Static COLL VM writer boundary

`ot_hgi_coll_static_vmwrite` replaces the transport/assembly portion of the historical credit-based `ot_hgi_coll_b2_vmport`. The historical module is preserved. This component is production-width RTL, but its standalone bench does not qualify an integrated die, SRAM service, remote ring or full collective program.

The compiler supplies five ingress reservations each cycle. Input lanes are RGX0–3 (512 data bits and 40 address bits each) and TKW (568 bits: address40, mask16, data512). An ingress valid must equal its reservation. This implementation accepts local VM main/mirror addresses only; an HBM-space RGX request faults. There is no ready output or dynamic issue condition.

For an input sampled at rising edge C, low-sector kq changes after C+1 and high-sector kq changes after C+2. Both edges are unconditional; payload capture continues even after a sticky fault. `launch_done` changes with the high sector and means launch only. A separate synchronous bank samples these output registers at C+2 and C+3. SRAM commit is a separate bank contract: the bank's three-edge sampled-request-to-commit path would commit at C+5 and C+6. Physical relay stages, different phases, and response sampling must be measured in the composition and added to the compiler calendar. Neither `launch_done` nor this bench proves memory commit.

Each of eight outputs is `{valid, sector16, data256, mask8}`. Sector is the existing COLL ABI `address[18:3]`, and bank is `sector[2:0]`. The high half uses sector+1. RGX masks are all ones; TKW low/high masks are preserved. Address bits39:19 and2:0 must be zero. Bits17:16 select sid, bit18 selects main/mirror; increments cannot cross a sid boundary.

The compiler additionally supplies `slot_valid[7:0]` and `slot_owner[31:0]` describing the kq output launched at the upcoming edge, with four bits per bank. Owners0–4 denote low halves of RGX0–3/TKW; owners5–9 denote their high halves. The calendar must match the complete output set exactly, including empty banks. Multiple halves using the same bank in a cycle are a resource conflict, even if the payload happens to match. The hardware reports a sticky fault; it does not pick a winning request, queue a request or move a write to another cycle. For an illegal program the conflicting payload is OR-combined and has no valid semantic interpretation. System fault handling must prevent use of that program's results.

There are exactly two bounded line stages, no FIFO occupancy to extend, and no admission counter. Four RGX lanes can run every cycle when first banks are0,2,4,6 and high halves occupy1,3,5,7. A five-lane simultaneous burst is also legal when TKW starts at bank1 and adjacent ingress cycles leave sufficient resource slots. The compiler must reserve capacity for all users of the bank, including non-COLL writers, through the H-VM explicit bank-owner interface.

`run_static_vmwrite_bench.sh` runs a bit-exact independent expected-output calendar at full port width. It checks a 24-cycle continuous four-lane burst, ten simultaneous five-lane bursts, exact per-half and launch_done timing, byte masks, sticky faults for extra reserved resources, ingress overflow, and bank conflicts, plus fault clearing on reset. Mutation1 corrupts a payload bit; mutation2 disables bank-calendar fault reporting. Both must fail. This bench uses ideal declared-boundary input stimuli and inspects actual RTL output; it contains no replacement SRAM or internal compute model.
