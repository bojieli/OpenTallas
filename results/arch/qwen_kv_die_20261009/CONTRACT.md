# Qwen3-8B ROM: ROM die + KV die interface contract (stream kv-die, 2026-10-09) — v1.0

**Owner decision (2026-10-09 ~04:00 PT).** The Qwen3-8B ROM design becomes a TP4 ROM die + KV die pair per package (option 1a of `results/arch/qwen_tp8_vs_sysdie_20261009/result.json`). KV never crosses the link.

The machine-readable form of this contract is `CONTRACT.json`, written by `tools/qwen_kv_die/contract.py`. The bench, the two die generators and the re-price all import that tool, so the numbers below cannot drift from the hardware they describe.

## 1. Partition

| 128 × per-PC CDC (`qkd_cdc` = `ot_qwen_stream4_cdc_pc`) | spine: SU64/SFU, banked VM, tree top, band slabs/lanes/serializers, constant ROM, sequencer + control |

| PLL and reset sequencer `qkd_pll` (the package clock and reset producer) | |
| KV-die sequencer `qkd_seq` = `ot_qkvd_kv_seq`, the KV end of the link `qkd_d2d` = `ot_qkvd_d2d`, and the UCIe macro | |

**What crosses.** Each layer, only these cross the link:
- q: 1,024 BF16 values;
- the new K/V: 512 FP8 values;
- the attention output: 1,024 FP32 values.

The 4 MiB of KV that each layer streams on each die stays on the KV die.

**Embedding boot.** The embedding boot load no longer uses the ROM die. It goes host → `qkd_host` → HBM.

## 2. The link

**PHY.** The link is one UCIe-A x64 module, `ot_qkvd_ucie_x64_phy`. Its abstract is in `physical/qwen_kv_die_phy` and is generated by `tools/qwen_kv_die/phy_gen.py`.

| Item | Value |
|---|---|
| Area | 0.6047 mm² on each die |
| Shoreline | 777.6 µm on each die |
| Signalling | 64 + 64 lanes at 16 GT/s, 1,024 Gb/s each way |
| Load | 548-b flit at 1.2 GHz = 657.6 Gb/s (64 % of raw) |
| Latency, FDI to far FDI | best 3 / typical 5 / worst 9 cycles |

The latency figures come from:
- best: CPMT 2022, < 2 ns;
- typical: JSSC 2026, 3.5 ns measured;
- worst: 2 × the measured value, ASSUMED.

**CRC and retry.** These are the job of the vendor's UCIe D2D adapter inside the macro. Our adapter checks the sequence number and fails closed.

**Flit (548 b).** One flit crosses each way per 1.2 GHz cycle while the link is up. Its fields are:
- `seq[7:0]`;
- the credit return, 4 × 2 b (field j belongs to the sender's RX class j);
- `dv`;
- `class[2:0]`;
- `word[527:0] = {tag[15:0], data[511:0]}`.

Idle flits carry credits only.

| Class | Name | Direction | Producer → consumer | Words | Format (tag / data) | Link buffer | On critical path |
|---:|---|---|---|---|---|---:|---|
| 0 | CTL | ROM→KV | sequencer `dc` → `qkd_seq` | 1 / layer (ATTN) + 1 / token (TOKEN) | `tag[15:12]` op: 1 = ATTN {`[13:0]` T = pos+1, `[21:16]` layer, `[63:32]` KV base}; 2 = TOKEN {`[17:0]` id, `[45:32]` position}; 3 = CSR_RSP | 4 | yes |
| 1 | Q | ROM→KV | SU `x3` (`x3_tag[10:8]`=1) → `qkd_astk` ×4 | 32 / layer | `tag[5:0]` beat; 32 BF16 q values, exactly as `attend()` consumes them | 32 | yes |
| 2 | KVN | ROM→KV | SU `x3` (`x3_tag[10:8]`=2) → `qkd_land` (merge + posted write) | 8 / layer | `tag[2:0]` {v, g, half}; 64 FP8 E4M3 bytes of the K (v=0) or V (v=1) row of KV head g at position T-1 | 8 | yes |
| 3 | EMBQ | ROM→KV | SU `ea` (r21c ABI) → gateway | 65 / token | `data[23:0]` address, `tag[0]` kind (64 code words, then the scale) | 32 | yes (per token) |
| 4 | RES | KV→ROM | attention hub → VM `ar` | 64 / layer | `tag[6]` g, `tag[5:0]` beat; 16 FP32 outputs; **`ar` widens 512 → 519 b** (it now carries the tag, because g = 0 and g = 1 can finish in either order) | 32 | yes |
| 5 | EMBD | KV→ROM | gateway `eq` → SU `eq` | 65 / token | a 64-code word, or the BF16 row scale | 32 | yes (per token) |
| 6 | HCTL | KV→ROM | `qkd_host` → sequencer `dh` | host-driven | `tag[15:12]` op: START, CSR_WR, CSR_RD, STOP; 8 = KV-die status/fault | 4 | no |

**Credits and flow control.** No hop waits on a same-cycle ready. Each hop is a credit loop:
1. **Producer → sender adapter.** The credits are the adapter's per-class input buffer. Each relay station carries data forward and one credit pulse back.
2. **Adapter → adapter, per class.** The credits are the far receive buffer and come back 2 b per class per flit. Each buffer is at least the worst link round trip (2 × PHY + 7 = 13 / 17 / 25 cycles), so every class streams one word per cycle.
3. **Receiver adapter → consumer.** The credits are the consumer's buffer.

**Ordering.** Order is preserved within a class. Classes are round-robin and independent. The KV die starts a layer only when CTL ATTN and all 8 KVN words have arrived. It forwards Q beats to the stacks as they arrive.

**When RES cannot stall.** The attention hub has no ready. A RES credit must therefore be in hand, or the sequencer raises a sticky fault. The buffering behind the hub is sized to hold a whole layer's 64 RES words:
- the KV adapter input buffer;
- the link buffer of 32;
- the ROM end's `OCR_AR` = 2 × ROM stages + 8.

So a VM stall of any length does not lose a word in that layer. The bench stalls the VM for 300 cycles.

**Registered boundaries.**
- Every adapter and sequencer input is captured in a flop at the pin, and every output is launched from a flop.
- The FDI runs from flop to macro on both dies, with no logic between the macro pins and the flops.
- Both dies place relay stations at most 430.56 µm apart.

## 3. Clocking and reset

| Item | Design |
|---|---|
| Clock domain | One 1.2 GHz domain on both dies, from the KV-die PLL |
| ROM-die clock | The PLL clock is forwarded on a dedicated differential bump pair beside the UCIe module (not a UCIe data lane). On the ROM die it runs `qfd_d2d_rom.pll_fwd_o` → `qfd_clkrx`, a deskew buffer that roots the same 121 region trunks the r21c hub drove. The two dies are mesochronous. |
| CDC | None in our logic. Each die's FDI runs on its local core clock, and the macro retimes the forwarded lane clock. The HBM 976.6 MHz domain and its CDC stay on the KV die. |
| Reset | The KV-die reset sequencer drives the `rst_fwd` bump, then `qfd_clkrx`: asynchronous assert, synchronous 2-flop release. From there it goes to the sequencer `rsi`, which carries it in its words as in r21c. |
| Link up | Training and the sideband are inside the macro (`tx_up`). Neither adapter sends before `tx_up`. |

**Measured (`bench.json`, ctx 8192).** The attention layer step, from the first ROM-face word to the last RES word at the VM, takes:
- **1,855 cycles** typical;
- 1,853 best;
- 1,867 worst.

That step contains:
- the KVN wait (8 words) before the attention starts;
- the near-HBM attention itself (R = 8);
- both crossings.

It replaces the 1,756 cycles of tile attention plus softmax_norm.

Per token, the embedding row takes 287 cycles typical and 614 worst. The token is 221,538 cycles = 5,416.7 tok/s (`reprice.json`).

## 6. Decisions absorbed from review-0327 (binding for every stream building on this contract)

**Class identity is queue identity; bit 10 is not a class bit.**
- On the link, a word's class is the flit's 3-bit class field, and each class has its own buffers end to end.
- Inside the KV die, the gateway and landing keep separate SU and HOST queues (J3, integrated SU8/HOST8). The queue a word sits in is its class.
- No tag bit carries class. In particular, the outer link-tag bit 10 is never decoded as EMB/BOOT. J1 showed that clearing it is unsafe, because sequence ≥ 1,024 uses it.
- At the ROM end, `x3_tag[10:8]` is a 3-bit class code at a single SU queue, with `tag[5:0]` = beat. It carries no sequence field, so the collision cannot happen.
- The embedding boot load (RAW / BOOT_WR / BOOT_END) no longer crosses the link. It runs host → `qkd_host` → landing/strip → HBM on the KV die (the HOST8 queue). The SU8 boot queue is not instantiated on r22k.

**J4: the ECC check-bit read is an ordinary scheduled read.**
- The SECDED check bits of the KV (and embedding) sectors in HBM are fetched by the KV-die controller (`qkd_ctrl`) as an ordinary descriptor read, scheduled with the data rows.
- There is no new typed request class and no separate provider.
- Nothing about ECC crosses the link. A KV row is corrected in `qkd_ctrl` before the CDC (Q7, approved). The KVN rows posted from the ROM die are written with their check bits by the same controller write path.

**J2: the hub SRAM chain is a measured fallback for the KV-die hub, not the default.**
- Its saving is ~92k µm² net per hub, from 4 links × 38,799 → 4,035 µm² std cells against 12 SRAM macros at 46,699 µm².
- It also adds +3 forwarded-clock edges.
- The default sizes the KV-die frames (gateway / landing link buffers, `qkd_ahub`) to ≤ 55 % utilisation.
- Use the fallback only if the KV-die centre column runs out of area. The track-capacity correction applies to all KV-die channel arithmetic: M4/M6 are conservative at 560 tracks, not 641.
