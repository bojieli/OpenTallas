# HBM-NEXT-ATT4 gate E1: exactness of the KV-line-stationary union stream (2026-10-19)

**Verdict: E1 PASS.** If each KV line is streamed once over the union of the 4 lanes' selections, and each lane applies only the lines its mask selects, every lane's attention is **bit-identical to that query run alone**. No reordering is involved: the golden's own list order is ascending, so each lane's subsequence of the union stream is exactly its golden list. This holds under conditions C1 to C5 below, and the RTL of this lane implements them. The ATT lanes therefore stay in scope; the D2 fallback (drop ATT lanes, 2,827 tok/s at P = 2) is not needed.

## 1. The reference summation order

Source: `tools/hdc_golden_v41.py`, at base `claude/hbm-next-1019@4f894f572`.

- **Main-model row list of one query (`Model.attention`):**
  - rows = `state["win"][L][-W:]`, the window rows **oldest first** (ascending position, W = 128);
  - then `[ckv[src][i] for i in ctx["sel"]]`.
  - `indexer()` returns `sel = sorted(topk_lowest_index(s, k))`, so the selections come **in ascending index**. The rank order of the top-k is discarded before attention.
- **`Model.attend`, two-pass softmax over the whole list** (`blocks = [all rows]`, the HBM contract; `osm` is not in `FUSE`):
  - s = dots(q, kvm) * scale; m = max; e = exp(s - m);
  - acc = dots(bf16(e), kvm.T); den = reduce_rows(e) + exp(sink - m); o = bf16(acc / den).
  - Every sum runs over the query's **own** list positions 0..T-1:
    - chunk8 (R-ARITH, `csum`): chunks of 8 consecutive list entries, each sequential from +0, then a pairwise tree padded with +0;
    - legacy: `dots` sequential from +0, `reduce_sum` with 8 interleaved partials by position % 8.
  - The QK dot of one row runs over the head dim only, so it does not depend on the other rows.
- **MTP verify (`forward_positions`, layer-major).** Position p+l has its own window (positions p+l-127 .. p+l) and its own selection (`ctx` per position). Lanes are consecutive positions.
- **DSpark draft (`dspark_attention`).** All block rows attend to the **same** kvm (window cache in ring-slot order + the block rows). The union equals every lane's list and every mask is all-ones, so this case is trivially exact.
- **Multi-user.** Lanes have disjoint KV. The masks are exclusive, and each lane's subsequence is again its own list.

## 2. The union stream and its exactness conditions

The stream order is:
1. the window positions of all lanes, ascending: p-127 .. p+3, which is 131 lines for 4 lanes;
2. then the union of all lanes' compressed selections, ascending.

Every line carries an NL-bit lane mask. Each lane's selected lines form an increasing subsequence of this stream: its window, then its own selections, both ascending. That subsequence is exactly the lane's golden list. The conditions are:

- **C1, list order.** The union is streamed in the canonical list order: window first, oldest first, then compressed rows ascending. The window ring therefore holds W + N - 1 rows (D2 §3.2: 256 slots). Streaming in rank order breaks exactness (negative control `rank`).
- **C2, per-lane ordinals.** A lane's chunk / partial boundaries, its last chunk and its pairwise padding are counted on its **own** ordinal. An unselected line gives the lane **no** beat: its ring slot circulates as a bubble and the line never enters as a +0 term. Zero insertion moves chunk boundaries and fails (negative control `zins`). Under legacy it is also detected, through the interleaved den partials.
- **C3, per-lane softmax state.** Max, exp, den and the sink are per lane. The SU receives each lane's score vector indexed by lane ordinal.
- **C4, SM partition on per-lane aligned runs.** Each lane's list is cut into the P = 1 aligned runs of nrun chunks (`sm_attn_bench.plan`: T 640 → 80 chunks → runs of 4 chunks = 32 ordinals).
  - An SM job is a set of (lane, run) pairs. It streams the sorted union of those runs' lines and publishes one node per (lane, run).
  - The cross-SM merge per lane is the P = 1 pairwise merge over that lane's nodes, in run order.
  - Smaller aligned runs (nrun / 2, nrun / 4) are equally exact; they only add nodes to the merge.
  - A fixed union-range split that cuts a lane's chunk at the SM boundary is **not** exact (negative control `fixsm`).
- **C5, causality of verify lanes.** Lane l may only select rows that exist at its position: compressed index < (p+l+1) / ratio, window ≤ p+l. All verify rows must be written (KVWB) before the attention record starts. Both are compiler / IDX properties: lanes HBM-NEXT-UNITS and CMTP own them.

## 4. Throughput consequence (scheduling note for CMTP / VEH; exactness unaffected)

The record time is set by the **most-loaded SM**, not by U / 32. Per-SM PV lines at T 640 and 4 lanes come from synth_chunk8. P = 1 runs 32 lines a query per SM, so 128 lines for 4 queries back to back.

Notes on the table:
- The model's ATT price (`hbm_plane_model.kv_union_ratio`, comp x U(N)/U(1)) assumes that per-SM work is proportional to the union.
- With the P = 1 aligned grouping, the disjoint case puts 128 lines on the top-k SMs, 17% above the model's upper bound.
- Spreading the (lane, run) jobs over all 32 SMs ("balanced": runs that share ≥ 25% of their lines stay grouped, LPT, runs halved or quartered when that balances better) stays under the model at every overlap.
- **Recommendation to CMTP:** the attention record's SM assignment must be the balanced one. It is computed at run time from the masks, like the MoE expert union. That makes the union length data-dependent, as the expert union already is. The span is fixed once the IDX union record is known (no handshake), but the static calendar must reserve either the price-of-record bound or a per-record span published with the union record. CMTP owns this.
