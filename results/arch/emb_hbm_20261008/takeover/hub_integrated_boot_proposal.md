# Integrated SU / HOST BOOT hub proposal — review only

Owner retarget: this is a component for the separate KV die/package serving Qwen TP4 ROM dies. Hub, embedding fetch, HBM PHY/landing, near-HBM attention and host/PLL reside on the KV die; KV payload does not cross to ROM. No r21c outline squeezing, new package fields, RTL or route is proposed here. The shared KV-die CONTRACT and log must determine actual integration interfaces and floorplan. The accompanying JSON pins the native sources and separates source inventory from analytical estimates.

Replace the native XS8 skid with two independent eight-entry queues, SU and qualified HOST BOOT, inside an additive, default-off hub variant. Keep the native input capture edge and queue-to-link-send edge. Keep the receive path, four CR128 link ledgers, registered outputs and embedding gateway unchanged. Selecting the queue for the actual native link send also selects the returned source credit; there is no owner FIFO or separate forwarding register. No tag bit identifies queue ownership.

Use full 512-data/11-tag packets, with the native stored destination2/broadcast1 metadata, in both queues. No host compaction is needed for the first proposal. Each producer's eight credits reserve all accepted packets, including its input capture pending enqueue. Only a true link send retires a reservation and returns that producer credit. A broadcast decrements all four link ledgers but returns one source credit. Simultaneous accept/send must be counted once, and pointer differences plus pending capture must never exceed eight. The currently source-bound KV CDC producer itself starts with two x3 credits, so an eight-slot hub does not imply that producer already sends eight outstanding packets.

Retain absolute gateway FETCH priority. Otherwise choose SU whenever its queue is nonempty; choose HOST only when SU is empty. A blocked SU head also blocks HOST, preserving conservative SU priority. Per-producer ordering holds; cross-producer ordering can differ from the separate merger's shared XS order. Continuous SU traffic can starve HOST, so no bounded boot service claim is made. HOST RAW qualification/packet mapping and allones BOOT_END mapping remain the already gated contract. The gateway snoops BOOT_END only at its actual link send, and readiness still needs all four ordered STATUS count/checksum matches.

Native and separate-merger counts come from declared source registers. The integrated inventory is a model, not synthesized area. It retains two 524-bit input packet/valid captures, two 8×526-bit queues, four four-bit queue pointers, two source-credit pulse registers, two queue fault bits and the common link-overflow bit. A 526-bit two-input head mux and new guard/control cost are priced with an initial 800 µm² allowance, not a measured ceiling. This saves 4,204 state bits / 1,345.28 µm² at the flop proxy versus the current combined implementation. Under the historical r21c SRAM-hub model it leaves 4,427.57 rather than 3,082.29 µm² for codec/control/buffers. Those old fit numbers are context only; the owner has moved these functions to the KV die and has not assigned its outline.

The intended capture-to-native-send minimum stays two core edges at 833.333334 ps; the current separate merger takes four. Removing its forwarding stage therefore saves two minimum forward edges and one source-credit register edge. These are analytical stage counts pending actual integrated gating. The previous measured marker acceptance372/send376/ready481 is historical evidence for the separate merger, not a measurement of this proposal. A added mux could require physical pipelining; any resulting edge must be measured and repriced.

The tag namespace is currently unresolved. Native `ot_qwen_kvc_hub_cdc` sends `td[481:471]`, all eleven sequence bits, as x3_tag. The embedding hub uses tag[10] as EMB class on transmit and receive, so seq1024..2047 alias that class. The current physical SU master exposes lane KV write ports rather than an x3/tag producer; its missing transport binding cannot establish a narrower tag domain. Separate queues solve credit ownership without solving this class collision.

Clearing only the outer KV tag bit10 is not safe for every existing consumer. The embedding hub drops the outer tag at ar_d, but all three actual native write-bridge variants use the identity hub in their tests. That hub preserves the full outer tag and source, and the bridges compare captured identity_tag with decoded payload seq[10:0]. Thus an unchanged payload can remain bit-exact while a normalized outer tag fails existing identity checks at high sequences. The codec does carry full seq16 in the payload, and the existing KV shift/receive inverse preserves its complete510-bit packet. A normalized outer class bit could be viable only with an explicitly reviewed receiver contract; this proposal neither changes that receiver nor invents a new bit. An exhaustive2048-sequence source-bound gate and deliberate high-sequence negative remain required.

Runtime HOST addr31=0 is rejected/unconsumed by BOOT queues and remains a separate owner. KVservice w_room/wd is not nativehost o_cr. The SOURCE64 runtime decoder and combined host credit binding remain OPEN. Plain flop queues/control have functional bounds/overflow guards only; no ECC, mirrors, TMR, auth, lease or epoch is added.

Claude review must precede integrated RTL. Thereafter the minimum actual hub/gateway gate must reach eight accepted outstanding packets per producer under CR128 backpressure, preserve packet/tag/order/reset/wrap behavior, return each credit to the correct queue and make readiness wait for all four STATUS replies. Payload and wrong-source/early-credit mutants must fail. Elaboration and mapped inventory run only under remote admission; actual mux timing, clock/pins, hub routing layers, SRAM escape and physical area must be checked before any route through Claude intake. No adoption or end-to-end KV-die claim follows from this proposal.
