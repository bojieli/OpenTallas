# Qwen finite programme store candidate

The released 1024-PW ABI cannot install the actual decode calendar: metadata occupies 480 PW and 390 entries need another 780 PW, beyond the 976-PW calendar ceiling. The original full-layer diagnostic needs 13,910 PW including table payloads. Moving tables alone does not fix calendar capacity. The source0d4c RTL boundary witness is committed separately at `f344a9570`, `results/rtl/qwen_layer_tput_1018/q_ready_programme/`: 248 entries seal, 249 and 390 fault.

The candidate separates the immutable calendar and local table payloads. Each of 12 slices has four concatenated 4096x266 ROMs. One stage occupies 106 rows: four already rewritten user PROG copies of six records each, 18 BTAB slots, and 64 CROM slots. All 36 stages occupy 3816 rows; 280 rows remain. An executing user reads exactly 88 addresses, selecting its six PROG records plus the common immutable BTAB/CROM payloads. User-specific CROM and BTAB write addresses select disjoint mutable regions. No payload arithmetic, compression, dynamic queue or readiness wait is introduced.

The production table contract pins PIDX_STRIDE128. CROM uses 128 sixteen-pair rows per user; BTAB uses 128 sixteen-BF16 words per user; PROG uses 128 instructions per user. These partitions fit the current physical arrays. This is distinct from proving complete live VM allocation inside UVM_STRIDE4096: the historical programme's large virtual addresses still need a real remapping certificate. A caller must supply four exact user PROG payloads and the source digest of that certificate. The packer refuses missing stages, partial user programmes, wrong table family shapes, overlapping addresses, oversized payloads and unpinned ABI parameters.

Source-pinned lowerer probe `oth-ubuntu-1554232-1792423654` ran on the fleet against the byte-identical three lowerers at `4e718c0107e99f869c95db0ecedcca8711577dff`. It confirmed PROG6 on every slice, BTAB counts `[18,16,18,16,18,16,18,16,14,12,14,12]`, CROM counts `[64,64,64,64,64,64,64,64,48,48,48,48]` after broadcast duplication, and 788 logical source records. The query used unit-valued scales for **shape only**; it did not generate production checkpoint table data.

Physical discussion with QW gate recovery proposes a 388.8x302.4 um outline for each four-ROM slice, with lattice origins `(43.2,43.2),(216,43.2),(43.2,172.8),(216,172.8)` and horizontal/vertical channels 50.976/66.69 um. These are proposed homes, not die-slot fit evidence. The 49-ROM raw area is 0.3755 mm²; 12 local outlines occupy 1.4109 mm². A dedicated calendar ROM at CTLM `(475.2,388.8)` requires the current CTLM outline to grow to 777.6x518.4 um. Existing mutable/control macros are retained in this sizing.

F16 admission is a separate storage plane: the selected model has 8216 lifecycle rows, three 4096-row macros, 14 address bits, period 8053632 requiring 23 bits, and 3260 OVL entries per list within the actual 4096-row OVL ROM with 12 address bits. These counts do not reduce table/calendar capacity. The exact admission artifact receipt and its macro family must be joined before combined area or native claims.

Fleet unit `oth-ubuntu-4077732-1792423983` passed four tests covering all 36 stages, 12 slices and four users, disjoint mutable partitions, physical via-mask readback at the last used row and high payload bit, and rejected capacity/provenance/shape cases. These are compiler/layout tests with synthetic payloads, **not** real-macro RTL, whole-programme installation/execution or SU/MU token qualification.
