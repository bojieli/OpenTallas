# Qwen finite programme store candidate

The released 1024-PW ABI cannot install the actual decode calendar: metadata occupies 480 PW and 390 entries need another 780 PW, beyond the 976-PW calendar ceiling. The original full-layer diagnostic needs 13,910 PW including table payloads. Moving tables alone does not fix calendar capacity. The source0d4c RTL boundary witness at `f344a9570`, `results/rtl/qwen_layer_tput_1018/q_ready_programme/`, proves 248 entries seal while 249 and 390 fault. The older 13,910 count is a decode-layer diagnostic, not the capacity of a complete release programme.

The candidate separates the immutable calendar and local table payloads. Each of 12 slices has four concatenated 4096x266 ROMs. One decode stage occupies 106 rows: four already rewritten user PROG copies of six records each, 18 BTAB slots, and 64 CROM slots. All 36 stages occupy 3816 rows; 280 remain. An executing user reads exactly 88 addresses, selecting its six PROG records plus the common immutable BTAB/CROM payloads. Payload bits are preserved. There is no dynamic queue or readiness wait.

The new opt-in compact table ABI uses decode BTAB bases `[0,272,344,416]`, each with 72 words. The immutable common LM-head region is `[72,272)`. All four decode regions plus the head region use 488 of 512 words. This avoids the head overlap caused by a uniform 128-word decode stride. CROM reserves 128 sixteen-pair rows per user, and PROG reserves 128 instructions per user. These partitions fit the current physical arrays. Shared head constants/programmes have not yet been lowered or installed; the tail has sufficient provisional room for a 98-record bound, but that is not an actual head image.

`emit_table_manifest.py` recovered all36 static payloads from the 36 TP4 die0 NPZs whose hashes are pinned by the existing preparation receipt. TP8 die0 uses the exact row subset established by `dv_layer_fixture.py`: qkv rows `0:512,1024:1152,1280:1408`, gate/up rows `0:3072`, and the true full-row o/down post-scales. These measurements qualify payload transport and finite storage isolation. They do not qualify numerical layer execution, a complete PW/DW installation, a head programme, a SU/MU token, physical timing or a release frequency. The calendar needs a real port budget. The current playhead fetches four128-bit entries per read, so preserving throughput/ages requires **two**266-bit calendar ROMs. The earlier one-ROM estimate was insufficient. Source probe `oth-ubuntu-1602696-1792425159` counts320 LM-head commands and64 embedding commands, in addition to390 decode commands:774 before BOOT/INIT/alignment. A10-bit count is necessary; legacy nent9 cannot represent it. The final complete calendar and ROM/count ABI remain OPEN. Existing10-bit start-first/count fields are not an excuse to truncate the descriptor count.
