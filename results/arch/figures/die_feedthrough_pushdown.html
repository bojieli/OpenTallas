Die feedthrough pushdown

How die-level wires get across the big blocks today, why that jams the channels, and what changes when the blocks carry the wires through themselves.

Relays and repeaters

A long die wire needs two different kinds of help, and they solve different problems.

Repeater: a plain buffer cell with no clock. A wire's delay grows with the square of its length and its edges get slower and slower. A repeater re-drives the signal with a sharp edge, so delay grows only linearly. The signal passes straight through in a few tens of ps, within the same clock cycle. In our dies these are BUFx12f-type cells inserted by repair_design, needed every ≤450 µm.
Relay: a clocked register (flip-flop) stage. Even with repeaters, a wire can only travel so far in one 833 ps cycle. A relay catches the bit at the end of the cycle and launches it again on the next, so a long path becomes several one-cycle hops and each relay adds one cycle of latency. In our dies a relay is a small hard macro holding a whole bus of flops, e.g. S81's dsfd_dvrlyh: 276–562 bits in about 26 × 17 µm.

What a feedthrough is

A feedthrough is a signal that enters a block and leaves it again without the block's logic using it. Instead of routing around the block, the wire becomes a pair of ports on the block, and the repeaters and pipeline flops it needs on the way become ordinary cells inside the block, placed and routed by the block's own flow.

The second idea is a layer budget set from the top down: blocks keep their own wiring on M1–M7, and M8/M9 stay free over every block for die wires. A die wire then runs straight over the blocks on the fast top layers and dips down only where a repeater or flop sits, inside the block it is crossing.

How commercial flows do it

Large GPUs, CPUs and network chips use a hierarchical flow in Cadence Innovus or Synopsys IC Compiler II / Fusion Compiler, with Tempus or PrimeTime for sign-off timing. Feature names below are generic; exact commands differ between tools and versions.

  1. Design planning on the flat chip. Load the whole netlist, place the hard macros, cut the chip into partitions, and run a quick trial placement and route to see where top-level wires want to go.
  2. Pin assignment with feedthrough insertion. The tool routes each top-level net across the partitions. Where a net only passes through a partition, it adds a feedthrough port pair to that partition and to its netlist. Pins are placed so neighbouring partitions line up when they touch.
  3. Pipeline and buffer pushdown. Repeaters and pipeline flops planned at top level are pushed into the partition each one lands in. Pipeline stages are usually fixed by architects in RTL from the measured top-layer reach; the tool only places them.
  4. Timing budgeting. Each top-level path's clock period is split into in-partition and cross-partition shares, giving each partition its own constraints.
  5. Parallel block implementation. Each partition is placed, clock-tree built and routed on its own, using the reserved layers and repeater sites from the plan.
  6. Abstracts and top assembly. Finished partitions become timing models (ETM / ILM) and LEF abstracts. The top level is mostly abutment, with only short glue routes, followed by hierarchical timing and ECO.

Registering every block pin, which our design already requires, is what makes the missing budgeting step manageable: every block-to-block path starts and ends at a flop, so each hop is a single known cycle.

What the new tooling does

OpenROAD has no feedthrough insertion, so these steps live in tools/die_feedthrough/. They run in this order:

  1. Census. Read each die's lanes and find which big blocks each lane's straight path crosses, and how many bits enter each block face.
  2. Plan. Pick lane routes, place flops every ≤ reach and repeater sites every ≤450 µm, and write a per-block spec of ports and in-block stages.
  3. Push down. Add the feedthrough ports and pipeline registers to each block's netlist, set M8/M9 pins aligned with the neighbouring block, and cap the block's own wiring at M7.
  4. Harden and check. Re-harden each block, probe its routing with the added traffic, then probe the die and re-derive the static schedule from the new stage counts.
