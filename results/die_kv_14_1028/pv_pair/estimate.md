## (b2) red_issue / red_capture broadcast: per-lane-group copies

**Load census (RTL, UNCHECKED count):** c_r[17] red_issue -> 16 lanes x (valid OR + 32 a-mux + 32 b-mux) = 1,040
+ lastp/wp[0]/tc = about 1,049 loads; c_r[18] red_capture -> 512 reduce_a enables. Worst TT path (CHECKED): QN 88.6 ps +
452 ps of buffering (CKINVDCx16 slew 66 -> 3 x BUFx6f -> BUFx5 fanout 64 slew 137) before the logic.

**Constraint found:** face_guard (`tools/die_plan/face_guard.py`, run by every kit after synth) requires every input
pin bit to load exactly ONE cell pin that leads to one flop. A zero-cycle copy of c_r[17] must load bc[17] on the same
edge, so copies cannot sit behind the one bc[17] pin. Copies from c_r would add a cycle (not allowed). Therefore
G copies = G pins: new port `bcx[2G-3:0]` with its own pin registers (group 0 keeps c_r[17]/c_r[18]).

**Choice G = 4 (lane l reads copy l*4/16):** per copy about 262 issue loads / 128 capture loads, local to 4 lanes (about 1/4
of the slice span). A planned 2-level fanout (about 16 per stage) gives about 50 ps clk->Q + 2 x 35 ps + 15 ps wire = **about 135-170 ps**
to the mux selects, against 541 ps today: **about 370 ps TT gain, against a 36 ps deficit** (UNCHECKED). G = 16 would save
about 40 ps more but needs +30 pins per slice; G = 4 needs **+6 pins per slice, +12 per pv_pair core** (1652 -> 1664).
0 added cycles; the column drives the copy pins from the same cmd[25]/cmd[26] bits (wiring outside the core).
