## Storage and physical architecture blockers before a successor kit

The current hub response_data is four runtime-selected 256-bit slots per client: 1024 bits for E/NW (N=1), 3072 bits for SW (N=3), excluding tags/state. The SW logical store exceeds the ~2kb rule. Merely dividing it into client declarations is not an SRAM solution. The operation can OR-arrive, clear and serve a same-edge bypass response; any real SRAM successor needs an exact port/lifetime model and clear-over-arrival priority proof. No drop-in OLD-read claim is made. A slot is reused only after its actual response retirement; no credit or backpressure may be introduced. Existing ring-stop payload arrays pl[0:3] and >=3-stage wide relay chains also require explicit ring/storage review; replacing delay FFs with SRAM must preserve one item/edge and actual read/capture delay, not just capacity.

Exact hub state inventory: per slot256 payload+16 tag+active1+writes1+expected3+seen3=280 bits, four slots/client, total1120*N bits (SW3360, E/NW1120). Request admission writes tag/expected/writes and clears payload; return updates OR payload and increments seen; a same-edge response uses accumulated payload OR current ret_f, and retires active. Admission has final priority over retirement for active/seen; clear has final priority over arrival for stored payload. A naive synchronous SRAM OLD-data read would not reproduce that same-edge bypass. Ten return sources (eight banks plus two ring directions) may present simultaneously; g5 already gives bank returns extra ages while ring returns remain direct. Their contribution is grouped OR with 3-bit arrival counts, not a one-arrival queue. Faulting traffic must continue to produce its historical data and sticky error, rather than being silently dropped. A proposed SRAM arrangement therefore needs a legal production per-slot arrival bound, simultaneously active client/slot schedule, source-specific bank/ring ages, explicit bypass/clear protocol and committed faulty-traffic equivalence. These are currently UNKNOWN, so no macro port count/area or new return-queue service rate is invented.

The current 648×1555.2 outline has aspect2.4 and ~4.4% SW standard-cell fill (44104um² from the original mapped textbook packet). Pin allocation, rather than logic area, drives this shape: the long ring face carries four2224-bit buses plus controls, about8900 contacts. At6/um that face alone needs about1484um. Shrinking to a ~300um logic square cannot carry those pins. A real successor must partition hard elements/landed ring boundaries and price their full-face geometry; neither a denser pin assignment nor a wider empty monolith is a safe fix.

All three masters currently have one clock root over a1555um parent. No failure is inferred from sink count or insertion alone. The >1mm parent requires actual local region trees with landed crossings, TT/FF spread<=80 and neighbor-matched boundaries. New region landings carry real edges; they are not modeled as zero-skew wire aliases. The existing DB3/DD4/DC3 and internal ring relays provide candidate cuts, but each cut must become a source-bound physical boundary and receive a complete pin-to-pin wire-stage bound <=405um. textbook reach0 means unmeasured. No actual-coordinate reach proof was produced here.

Thus complete candidate macro count/area/clock load, 40–60% usable fill or justified pin-bound partition, PG/contact geometry, routing demand/capacity and global latency are NULL pending those architectural choices. This is an explicit build blocker, not an omitted cost. Current macro count is zero. Proposed local predicate copies add no new memory port bandwidth; they do not resolve storage or global clocking. No new engine build or gate is ready.
